# Описание системы

В этом документе описаны основные типы скриптов (агентов) (на примере модуля `Symbol`) и правила их поведения.

---

## 1. Определение модуля

Модуль — это самостоятельная, изолированная часть приложения, реализующая одну бизнес-сущность. Каждый модуль содержит:

- **Собственный агрегат** (Domain Aggregate) — главную модель с бизнес-правилами и invariant’ами.
- Набор слоёв (api, app, biz, domain, infrastructure), обеспечивающих чёткое разделение ответственности.
- CRUD-конфиг (`*.mocrud.config.ts`) и
- Точку регистрации в NestJS (`*.module.ts`).

Модуль легко выносится, переиспользуется и тестируется независимо.

**ВАЖНО!** В системе реализован собственный generic-CRUD модуль, который для каждого другого модуля создает всю инфракструктуру для выполнения следующих действий:
Commands
createOne - создание 1 экземпляра сущности
createMany - создание 1+ экземпляра сущности
deleteOne - удаление 1 экземпляра сущности
deleteMany - удаление 1+ экземпляра сущности
updateOne - обновление 1 экземпляра сущности
updateMany - обновление 1+ экземпляра сущности
Queries
findOne - поиск 1 экземпляра сущности
findMany - поиск 1+ экземпляра сущности
Events
createdOne - 1 экземпляр создан
createdMany - 1+ экземпляр создан
deletedOne - 1 экземпляр удален
deletedMany - 1+ экземпляр удален
updatedOne - 1 экземпляр обновлен
updatedMany - 1+ экземпляр обновлен
foundOne - 1 экземпляр найден
foundMany - 1+ экземпляр найден
Настройки CRUD-модуля делаются в CRUD-конфиге

## **ВАЖНО!** Для каждого типа агента созданы ШАБЛОНЫ (TEMPLATES), в которых прописаны правила работы и создания на их основе действующих агентов. Их надо придерживаться.

## 2. Слои модуля и их ответственность

Ниже перечислены стандартные слои в любом модуле и краткое описание их ролей:

- **api** (`/api`)

  - Внешний интерфейс модуля - для приема и отправки запросов вне приложения:
    - DTO внешнего API (`dtos/*.api.dto.ts`) - содержат объект, упакованный в item / items[]
    - Контроллеры (`controllers/*.controller.ts`) - принимают HTTP-запросы и возвращают `IHttp_Response`
    - WebSocket-шлюзы (`gateways/*.gateway.ts`) - для пуш-уведомлений (асинхронные запросы)
      - Порты (`ports/*.port.ts`) - для доступа к внешним сервисам и хранилищу

- **app** (`/app`)

  - Внутренний CQRS-слой - для приема и отправки запросов между модулями приложения.
    **ВАЖНО!** Все взаимодействие между модулями происходит ТОЛЬКО через app-слой! Прямое обращение к "чужому" модулю либо отправка CQRS-объектов не через app-слой ЗАПРЕЩЕНЫ! (т.е., условно говоря, агенты из /biz, /domain, /infrastructure слоя не могут сами публиковть CQRS - только через app-слой)

    - CQRS-объекты (`cqrs/commands/*.command.ts`, cqrs/queries/_.query.ts`, `cqrs/events/_.event.ts`) - Commands, Queries, Events для взаимодействия между модулями
      - DTO для CQRS (`dtos/*.app.dto.ts`) - содержат объект, упакованный в item / items[]
    - Паблишеры (`publishers/*Publisher`) - для публикации исходящих команд/событий/запросов
    - Хэндлеры (`handlers/*Handler`) - для приема входящих команд/событий/запросов
      - Порты (`ports/*.port.ts`) - для доступа к внешним сервисам и хранилищу

- **biz** (`/biz`)

  - Собственно бизнес-логика:
    - Сценарии (Use Cases) (`usecases/*.usecase.ts`) - непосредственно бизнес-логика, которую необходимо реализовать
    - Функции (`functions/*.function.ts`) - если необходимо вынести часть бизнес-логики в отдельную функцию для удобства
    - Порты (`ports/*.port.ts`) - для доступа к внешним сервисам и хранилищу

- **domain** (`/domain`)

  - Доменные модели:
    - Объекты (`objects/*.object.ts`) - для входа/выхода бизнес-логики; описание объектов, на которых строятся агрегаты
      - Агрегаты (immutable модели) (`aggregates/*.aggregate.ts`, `aggregates/methods/*.ts`) - строятся на основе Objects, имеют собственные методы. Неизменяемы
      - Value Objects (`value-objects/*.vo.ts`) - в случае необходимости реализации сложной бизнес-логики. Вызываются через размещение декоратора (`@VOField(VALUE_OBJECT_CLASS)`) на поле в объекте

- **infrastructure** (`/infrastructure`)

  - Техническая реализация:
    - Сущности TypeORM (`entities/*.entity.ts`) - для связи с БД
    - Репозитории (`repositories/*.repository.ts`) - для работы с БД
    - Мапперы (Entity ↔ Aggregate и JSON) (`mappers/*`) - при необходимости сложного маппинга
    - Сидеры (`seeders/*`) - для создания объектов при запуске системы / регистрации нового пользователя
    - прочие утилиты/адаптеры/процессоры - для реализации специфической логики

- **symbol.crud.config.ts** (в корне модуля)

  - Конфигурация CRUD-модуля (`ICrud_Module_Config`): связывает все DTO, команды, обработчики и хуки для базовых операций

- **symbol.module.ts** (в корне модуля)
  - Сборка модуля Nest: включает импорты (TypeOrm, CRUD-модуль), провайдеры всех слоёв, контроллеры и экспорты

## API-слой

### Controller (`*Controller`)

**Назначение**

- Принимает HTTP-запросы от клиента.
- Валидирует входные DTO, добавляет/пропагирует `correlationId`.
- Публикует CQRS-команду через `CommandBus` и возвращает клиенту `IHttp_Response`.

**Правила поведения**

1. Класс-наследник `Controller_Port`.
2. Декорируется `@Controller.Decorator(<namespace>)`.
3. Методы обрабатывают один тип операции:
   - `@Post('add-symbols') createOne(...)`
   - `@Get`, `@Put`, `@Delete` и т.д.
4. Используют `this.baseCommand(...)` (или `baseQuery`) для унификации обработки:
   - Генерация и проверка DTO.
   - Установка `correlationId`.
   - Обработка ошибок в одном месте.
5. Всегда возвращают `IHttp_Response` со статусом, сообщением и данными.

---

## Gateway (`*Gateway`)

**Назначение**

- Обеспечивает websocket-коммуникацию с фронтендом.
- Гарантированно доставляет события (буферизует, если клиент ещё не подключён).

**Правила поведения**

1. Наследуется от `Gateway_Port`.
2. Декорируется `@WebSocketGateway({ namespace: '/<aggKey>' })`.
3. Логика:
   - `handleConnection` — клиент подключается, присоединяется к комнате `correlationId`.
   - Методы `emit*` используют `safeEmit(corrId, eventName, payload)`.
   - Если слушателей нет — сообщение буферизуется и отсылается при подписке клиента.

---

## APP-слой

### Handler (`CommandHandler`, `QueryHandler`, `EventHandler`)

**Назначение**

- Обрабатывает CQRS-объекты (Command, Query, Event_Class).
- Валидирует входные DTO, распаковывает дто, вызывает `UseCase`, (при необходимости) возвращает результат.

**Правила поведения**

1. Декорируется `@CommandHandler(SomeCommand)` / `@QueryHandler(SomeQuery)` / `@EventsHandler(SomeEvent)`.
2. Наследуется от `CommandHandler_Port<Command, InputDto, OutputDto>` / `QueryHandler_Port<Command, InputDto, OutputDto>` / `EventHandler_Port<Command, InputDto>`.
3. Всегда сохраняет `correlationId` из DTO в выходном DTO`.

---

### Publisher (`CommandPublisher`, `QueryPublisher`, `EventPublisher`)

**Назначение**

- Отправляет commands/queries/events в `CommandBus` / `QueryBus` / `EventBus` соответственно (CQRS).
- При необходимости маппит объекты в формат, необходимый для CQRS-объектов.
- Инкапсулирует логику публикации (включая установку `correlationId`).

**Правила поведения**

1. Наследуется от `CommandPublisher_Port` / `QueryPublisher_Port` / `EventPublisher_Port`.
2. Внедряет `CommandBus` / `QueryBus` / `EventBus`.
3. Запаковывает входящие объекты в DTO-формат.

---

## BIZ-слой

### Use Case (`*UseCase`)

**Назначение**

- Инкапсулирует бизнес-логику.
- (при необходимости) Отделяет «быстрый» ответ контроллера от «тяжёлой» фоновой обработки.
- Работает с портами для доступа к инфраструктуре.

**Правила поведения**

1. Наследуется от `Usecase_Port<Request_Data, Success_Data>`.
2. Реализует методы:
   - (опционально) `beforeMain(inquiry)` — действия ДО основной логики.
   - `runUseCase(input)` — основная логика.
   - (опционально) `afterMain(result)` — действия ПОСЛЕ основной логики.
3. **Ports**: зависимости (через конструктор) — абстракции `Symbol_AddSymbols_Port`, `Symbol_EventPort`, `Symbol_ProcessSymbols_CommandPort`, `Symbol_FindSymbols_Port`. ВАЖНО! Не имеет права сам публиковать CQRS запросы - только через связку port/publisher!
4. Фоновые операции запускаются внутри `safeExecute`, ошибки не должны «убивать» процесс.

## DOMAIN-слой

### Доменные объекты (`*Object`)

**Назначение**

- Определяют структуры входных и выходных данных для Use Case и других агентов.
- Служат «контрактом» между слоями.

**Правила поведения**

1. Классы наследуются от простых DTO (без логики).
2. Декорируются class‑validator-аннотациями (`@IsString()`, `@IsArray()`, `@ValidateNested()` и т.п.).
3. Не содержат бизнес‑логики — только описание полей и их валидацию.
4. При необходимости внедрения бизнес-логики создается отдельныйvalue-object, а объект помечается декоратором `@VOField(VALUE_OBJECT_CLASS, () => OBJECT_CLASS)` для трансформации "Object -> Value Object".

---

### Агрегаты (`*Aggregate`)

**Назначение**

- Моделируют главную бизнес‑сущность как неизменяемый объект.
- Инкапсулируют инварианты и операции над состоянием.

**Правила поведения**

1. Наследуются от `XXX_Object` и декорируются `@Aggregate()`.
2. Реализуют методы:
   - `static create(raw: main.IRecord)` — создание нового экземпляра;
   - `update(props: Partial<...>)` — возвращает новый агрегат с изменениями;
   - `toObject()` — маппит агрегат в DTO‑объект.
3. Вся логика проверок и инвариантов выполняется внутри этих методов.
4. Не используют внешние зависимости напрямую — только через порты/Use Case.

---

### Value Objects (`*VO`)

**Назначение**

- Представляют атомарные, неизменяемые типы (обёртки над примитивами).
- Обеспечивают валидацию и безопасное преобразование значений.
- Используются только в том случае, если необходима бизнес-логика, нереализуемая через calss-validator / class-transformer

**Правила поведения**

1. Наследуются от `AVO<T>`.
2. Хранят единственное поле `_value: T`, проверяемое через `@IsDefined()`.
3. Реализуют `toJSON()` и `valueOf()` для корректной сериализации и примитивного поведения.
4. Не содержат побочных эффектов и внешних вызовов.

---

## INFRASTRUCTURE-слой

### Сущности TypeORM (`*Entity`)

**Назначение**

- Описывают схему БД и связи между таблицами.
- Отражают поля доменной модели в виде колонок и связей.

**Правила поведения**

1. Классы декорируются `@Entity()`, `@Column()`, `@ManyToOne()`, `@Index()`.
2. Именование: `<EntityName>_Entity`.
3. Вложенные объекты оформляются отдельными Entity-классами (например, `Symbol_Country_Entity`).
4. Не содержат бизнес‑логики — только описание структуры.

---

### Репозитории (`*Repository`)

**Назначение**

- Инкапсулируют операции с БД над Entity через TypeORM.
- Маппят Entity ↔ Aggregates и отдают обратно агрегаты.

**Правила поведения**

1. Наследуются от `Repository_Port<Entity>`.
2. "Из коробки" предоставляют методы:
   - `createOne`, `createMany`, `updateOne`, `updateMany`, `deleteOne`, `deleteMany`, `findOne`, `findMany`.
3. Не содержат бизнес‑правил — только операции сохранения и выборки.

---

### Мапперы JSON (`*Mapper`)

**Назначение**

- Преобразуют данные между domain-объектами и внешними форматами (например, CalcInput).
- Разворачивают и упаковывают `customFields`.

**Правила поведения**

1. Наследуются от `CustomFields_Mapper_Port<S, D, K>`.
2. Определяют массив `mapping: CF_Map<…>[]` с `pathA` ↔ `pathB`.
3. Указывают `forwardContainers` и/или `backwardContainers` для работы с `CustomField[]`.
4. Не содержат сложной логики — только чистые правила трансформации.

---

### Сидеры (`*Seeder`)

**Назначение**

- Заполняют БД начальными данными и конфигурацией (табличные пресеты).
- Существуют следующие варианты сидеров:
  - `onBootstrap.feature.seeder` - выполняется при старте приложения. Используется для сущностей, не привязнных к user (т.е. не нужно создавать новые экземпляры сущностей для каждого пользователя)
  - `onUserCreated.feature.seeder` - выполняется при создании нового пользователя. Используется для сущностей, привязнных к user (т.е. нужно создавать новые экземпляры сущностей для каждого пользователя)
  - `table-preset.seeder` - выполняется при создании нового пользователя. Используется для описания табличного вывода сущностей "по умолчанию" (в дальнейшем пользователь может изменить)
- Автоматически выполняются при старте приложения или при регистрации нового пользователя.

**Правила поведения**

1. Наследуются от `Seeder_Port<InputDto, Command>` или `OnUserCreated_Seeder_Port<InputDto, Command>`.
2. Реализуют методы:
   - `buildSeedInput()` / `buildSeedInputForUser(userId)` — формируют DTO;
   - `buildSeedCommand(dto)` — создают CQRS‑команду.
3. Не содержат фоновой логики — только отправку команд через `CommandBus`.

---

### Адаптеры / Процессоры / Сервисы

**Назначение**

- `Adapter_Port` — единая точка входа для адаптации данных к внешним сервисам.
- `Processor_Port` — фоновые задачи (Job‑based).
- `Service_Port` — утилиты и интеграции.

**Правила поведения**

1. Наследуются от `Adapter_Port`, `Processor_Port` или `Service_Port`.
2. Реализуют метод `run(...)` (или `processJob`, `execute(...)`), обёрнутый в `safeExecute`.
3. Логируют начало и результат выполнения.
4. Не содержат domain‑логики — только технические операции и интеграции.

## Рекомендации по единообразию

- **Именование**:

  - Контроллеры: `Entity_Action_Controller`.
  - Шлюзы: `Entity_Event_Gateway`.
  - UseCase: `Entity_Action_Usecase`.
  - Обработчики: `Entity_Action_CommandHandler` / `Entity_Event_EventHandler`.
  - Публикаторы: `Entity_Action_CommandPublisher` / `Entity_Find_QueryPublisher` / `Entity_Event_EventPublisher`.
  - и т.д.

- **Логгирование**: всегда через `this.logger.log|warn|error|success|important`.

- **Корреляция**: всегда сохранять и передавать `correlationId` между слоями.

- **Безопасность**: операции, которые не должны прерывать основной поток (фоновые задачи), выполнять через `safeExecute`, чтобы отлавливать и логировать ошибки без падения процесса.

- **Валидация**: DTO валидируются на входе (в контроллере и в обработчиках), результаты — на выходе.
